## Notes

### What is an algorithm?

An **algorithm** is a set of step-by-step instructions that solves a problem or completes a task. A good algorithm is **finite** (it ends), **unambiguous** (each step has only one meaning), in the **correct order**, and produces the **correct output** for any valid input.

Algorithms can be shown as: a **written description**, a **flowchart**, **pseudocode**, or **program code**. They all describe the same thing; the exam may give you one and ask you to produce another.

### Computational thinking: decomposition and abstraction

**Decomposition** means breaking a large problem into smaller sub-problems that are easier to solve. Each sub-problem can become its own **subprogram** (procedure or function).

Why it helps (exam points): easier to understand and design; different people can work on different parts at the same time; each part can be tested separately; parts can be reused; errors are easier to find.

*Example – a quiz game:* get the questions → ask a question → check the answer → update the score → show the final score. Each of these is a sub-problem.

**Abstraction** means removing unnecessary detail so you keep only what matters for the problem. The result is a **model** of the real world.

*Examples:* the London Underground map ignores real distances and street layout and shows only stations and connections. A bouncing-ball simulation might keep only position, speed and gravity, and ignore the ball's colour, brand and material.

Exam wording: decomposition = "breaking the problem down into smaller parts"; abstraction = "hiding or removing unnecessary detail / focusing on the important features".

### Analysing a problem: inputs, outputs, processing, initialisation

Before writing an algorithm, ask four questions.

| Question | Example: average of three test marks |
|---|---|
| **Inputs** – what data comes in? | the three marks |
| **Outputs** – what must come out? | the average |
| **Processing** – what must be calculated or decided? | add the marks, divide by 3 |
| **Initialisation** – which variables need a starting value? | a running total set to 0, a counter set to 0 |

Forgetting initialisation is a classic error: a total that never starts at 0 gives wrong answers.

### The three constructs

- **Sequence**: instructions run one after another in order.
- **Selection**: the algorithm chooses a path using a condition (IF … THEN … ELSE).
- **Iteration**: the algorithm repeats instructions (a loop).

Every algorithm in the course is built from these three.

### Flowchart symbols (Appendix 6)

| Symbol | Shape | Meaning |
|---|---|---|
| Terminator | rounded box (oval) | **start** and **end** of the algorithm |
| Process | rectangle | something to do, e.g. `total ← total + mark` |
| Decision | diamond | a yes/no question; two exits labelled **Yes/No** (or True/False) |
| Input/output | parallelogram | getting data in or showing data out |
| Flow line | arrow | shows the order of steps |
| Subprocess | rectangle with double side lines | a step defined in a separate flowchart (a subprogram) |

Rules for marks: one **Start**, one **End**; every box has an arrow in and an arrow out (decisions have two out); every decision exit is labelled; a loop is drawn by an arrow going back up to an earlier box.

A text version of a flowchart that repeats until a valid mark is entered:

```
(Start) → /Input mark/ → <mark between 0 and 100?> —No→ back to /Input mark/
                                    |
                                   Yes → /Output mark/ → (End)
```

### Pearson pseudocode (Appendix 5)

In the written paper, code questions use this style. It is not Python, so learn the keywords.

| Idea | Pearson pseudocode |
|---|---|
| Assignment | `SET Total TO 0` |
| Output | `SEND 'Hello' TO DISPLAY` |
| Input | `RECEIVE Mark FROM (INTEGER) KEYBOARD` |
| Selection | `IF Mark >= 50 THEN … ELSE … END IF` |
| Loop with condition first | `WHILE Total < 100 DO … END WHILE` |
| Loop with condition last | `REPEAT … UNTIL Go = 10` (runs at least once) |
| Counted loop | `FOR Index FROM 1 TO 10 DO … END FOR` (optional `STEP 2`) |
| Repeat n times | `REPEAT 5 TIMES … END REPEAT` |
| Comment | `# this is a comment` |
| Join strings | `SEND 'Score: ' & Score TO DISPLAY` |

Operators: `+ - * /` and `^` (power), `MOD` (remainder), `DIV` (whole-number division). Comparisons: `= <> < <= > >=`. Logic: `AND OR NOT`. Data types: INTEGER, REAL, BOOLEAN, CHARACTER (and STRING). **Indices start at 0.** `LENGTH(x)` gives the length of an array or string.

Example, in pseudocode:

```
SET Total TO 0
FOR Count FROM 1 TO 3 DO
   RECEIVE Mark FROM (INTEGER) KEYBOARD
   SET Total TO Total + Mark
END FOR
SET Average TO Total / 3
IF Average >= 50 THEN
   SEND 'Pass' TO DISPLAY
ELSE
   SEND 'Fail' TO DISPLAY
END IF
SEND Average TO DISPLAY
```

The same algorithm in Python (this is what you type in Paper 2):

```python
total = 0
for count in range(3):
    mark = int(input("Enter mark: "))
    total = total + mark
average = total / 3
if average >= 50:
    print("Pass")
else:
    print("Fail")
print(average)
```

Notice: Python's `range(3)` gives 0, 1, 2 (three loops). The pseudocode `FOR Count FROM 1 TO 3` includes both ends. Python needs `int(...)` because `input()` returns text.

### Reading and tracing an algorithm

To find the **purpose** of an algorithm, trace it with a small example and look at the output. Then state it in one sentence that mentions the data, e.g. "It adds up the numbers entered until 0 is entered, then outputs the total." Do not describe line by line ("it sets total to 0, then…") unless asked to *describe how it works*; that earns fewer marks than saying what it achieves.

### Finding and correcting errors

Typical algorithm errors:
- **Wrong condition**: `>` instead of `>=` (boundary mistake), `AND` instead of `OR`.
- **Wrong loop count**: loop runs one time too many or too few.
- **Missing initialisation**: total or counter never set to 0.
- **Wrong order**: output placed inside the loop instead of after it.
- **Never-ending loop**: the loop variable is never changed.

Method: choose test data that checks the boundaries, trace it, find where the output first goes wrong, and fix that line.

### Fitness for purpose

An algorithm is **fit for purpose** if it meets the stated requirements: it gives correct output for all valid inputs (including boundary values), deals with invalid input, and does so efficiently (no unnecessary steps or repeated work). Judge it with logical reasoning and test data, then say which requirements are met or not.

### Readable code (links to Paper 2)

Use **descriptive names** (`total_cost`, not `x`), **comments** to explain what a section does, and **indentation** to show structure. This makes programs easier to read, debug and maintain.

## Key terms and definitions

- **Algorithm**: a sequence of steps/instructions that solves a problem or completes a task.
- **Decomposition**: breaking a problem down into smaller, more manageable sub-problems.
- **Abstraction**: removing or hiding unnecessary detail so that only the important features of a problem are shown.
- **Sequence**: instructions carried out one after another in order.
- **Selection**: choosing which instructions to carry out depending on a condition.
- **Iteration**: repeating a set of instructions (a loop).
- **Flowchart**: a diagram that uses standard symbols and arrows to show the steps of an algorithm.
- **Pseudocode**: a structured, language-independent way of writing an algorithm that looks like code but is not tied to one programming language.
- **Initialisation**: giving a variable its starting value before it is used.
- **Subprogram**: a named, separate block of code that performs a specific task (a procedure or function).

## Worked examples

**1. A teacher wants a program that reads three marks, then outputs the average and "Pass" if the average is 50 or more. Write the algorithm in pseudocode. [5]**

Model answer: the pseudocode in the Notes above. Marks are earned for: inputting three values using a loop or three RECEIVE lines (1); adding them to a total that starts at 0 (1); calculating the average correctly (1); a correct IF with `>= 50` (1); outputting the result and the message (1). Any valid method is accepted; you do not have to copy Pearson syntax exactly, but it must be clear.

**2. A shop's program has to take an order, work out the total price and print a receipt. (a) Explain how decomposition could be used. [2] (b) Give one benefit. [1]**

(a) Split the task into smaller sub-problems, e.g. enter the items, calculate the total, apply any discount, print the receipt (1), and write each as a separate subprogram (1). (b) Each part can be tested separately / different programmers can work on different parts / parts can be reused (any one, 1).

**3. What does this algorithm do? [2]**

```
SET Total TO 0
RECEIVE Number FROM (INTEGER) KEYBOARD
WHILE Number <> 0 DO
   SET Total TO Total + Number
   RECEIVE Number FROM (INTEGER) KEYBOARD
END WHILE
SEND Total TO DISPLAY
```

It adds up the numbers the user enters (1) until 0 is entered, then displays the total (1). The 0 is not added. This is a "rogue value" or sentinel: a special value that ends the input.

**4. A flowchart has the decision "Is age ≥ 18?" with Yes leading to "Adult" and No leading to "Child". Write this as pseudocode. [3]**

```
IF Age >= 18 THEN
   SEND 'Adult' TO DISPLAY
ELSE
   SEND 'Child' TO DISPLAY
END IF
```

One mark for the condition with the correct comparison, one for the Yes branch, one for the No branch (ELSE).

## Common mistakes

- Using a diamond for an action, or a rectangle for a decision. Diamonds are only for yes/no questions, and both exits must be labelled.
- Forgetting the **Start** or **End** symbols, or leaving a box with no outgoing arrow.
- Not initialising a total or counter to 0.
- Writing `=` for assignment in pseudocode: Pearson uses `SET x TO value`; `=` is a comparison.
- Off-by-one errors: `FOR i FROM 1 TO 10` runs 10 times, but Python's `range(1, 10)` runs 9.
- Mixing up decomposition (splitting the problem up) with abstraction (leaving detail out).
- Answering "what does the algorithm do?" line by line instead of giving its overall purpose.
- Saying "abstraction makes it simpler" with no explanation of *what* is removed.
