## Notes

### Subprograms: procedures and functions

A **subprogram** is a named block of code that does one job. You **define** it once and **call** it whenever you need it.

| | Procedure | Function |
|---|---|---|
| Does a job | yes | yes |
| **Returns a value** to the code that called it | **no** | **yes** (`RETURN`) |
| Example use | display a menu | calculate an average |

**Benefits of subprograms** (exam points): code is written once and **reused**, so the program is shorter; the program is **easier to read**, debug and test, because each part is small; the work can be **shared** between programmers; a change needs making in only one place.

Pearson pseudocode:

```
PROCEDURE ShowMenu ()
BEGIN PROCEDURE
   SEND '1. Play' TO DISPLAY
   SEND '2. Quit' TO DISPLAY
END PROCEDURE

FUNCTION Average (Mark1, Mark2, Mark3)
BEGIN FUNCTION
   SET Total TO (Mark1 + Mark2 + Mark3) / 3
   RETURN Total
END FUNCTION

ShowMenu ()
SET Result TO Average (60, 70, 80)
```

Python:

```python
def greet(name):                    # procedure: no return value
    print("Hello", name)

def average(m1, m2, m3):            # function: returns a value
    total = m1 + m2 + m3
    return total / 3

greet("Ana")                        # Hello Ana
result = average(60, 70, 80)        # result holds 70.0
print(result)
```

**Parameters** are the names in the definition (`m1`, `m2`, `m3`): they receive data **into** the subprogram. The values you pass when calling (`60, 70, 80`) are the **arguments**. A **return value** passes data **out**. A function's result must be **used** (stored or printed) by the caller; just calling `average(60, 70, 80)` does nothing visible.

**Built-in / library subprograms** already exist, so you reuse them instead of writing your own: `LENGTH()` and `RANDOM()` in pseudocode; `len()`, `round()`, `abs()`, `int()`, `input()`, `print()`, `random.randint()` and `math.sqrt()` in Python.

### Local and global variables

- A **local variable** is declared inside a subprogram and exists only while it runs. Other parts of the program cannot see it.
- A **global variable** is declared outside all subprograms and can be used anywhere.

```python
counter = 0                  # global

def bad():
    counter = 5              # creates a NEW local variable; global unchanged
bad()
print(counter)               # 0

def inc():
    global counter           # say we want the global one
    counter = counter + 1
inc()
print(counter)               # 1
```

Prefer **local** variables and parameters: they avoid accidental changes, the same names can be reused in different subprograms, and memory is freed when the subprogram ends. Overusing globals makes bugs hard to find.

### Validation

**Validation** is an automatic check that the data entered is **reasonable and allowed** by the program. It does **not** prove the data is correct (a user typing age 21 instead of 20 passes any check). Validation makes programs **robust**, preventing crashes and bad data being stored.

| Check | What it tests | Example |
|---|---|---|
| **Range** | value lies between limits | mark between 0 and 100 |
| **Length** | number of characters | password at least 8 characters |
| **Type** | right data type | age is an integer |
| **Presence** | something has been entered | name not left empty |
| **Format** | follows a pattern | email contains `@`; postcode layout |

Validation is done with a loop that **repeats the question until the input is valid**, and an error message:

```python
def get_age():
    while True:
        text = input("Age (0-120): ")
        if not text.isdigit():                 # type + presence check
            print("Please enter a whole number")
        else:
            age = int(text)
            if 0 <= age <= 120:                # range check
                return age
            print("Age must be between 0 and 120")

def valid_password(p):
    return len(p) >= 8 and any(c.isdigit() for c in p)   # length + contains a digit

print(valid_password("abc12345"))      # True
print(valid_password("short1"))        # False (too short)
print(valid_password("longpassword"))  # False (no digit)
```

Note `isdigit()` is False for an empty string and for negative numbers such as `"-5"` (the minus sign), so it also rejects those. Good error messages tell the user **what was wrong and what to do**.

### Types of error

| Error | Cause | When it appears | Example |
|---|---|---|---|
| **Syntax** | breaks the rules of the language | before/when the program starts; it won't run | `print("Hi"` (missing bracket), `fro i in range(3):` |
| **Runtime** | program starts but **crashes** while running | during execution | dividing by zero, index out of range, `int("abc")`, file not found |
| **Logic** | program runs but gives **wrong results** | no error message | `a + b / 2` instead of `(a + b) / 2`; `>` instead of `>=` |

Logic errors are the hardest to find because nothing crashes. Find them by **testing** with data where you know the answer, and using a **trace table** or print statements.

Python's error messages tell you the **type of error** and the **line number**, e.g. `IndexError: list index out of range` on line 7, or `ValueError: invalid literal for int() with base 10: 'abc'`. Read the last line first, then go to that line and check the line above too.

### Testing

**Testing** checks that the program works, finds errors, and shows it meets the requirements. A **test plan** is written before testing and lists, for each test: the **data**, the **type of data**, the **expected outcome** and (after the test) the actual outcome.

Three types of test data:

| Type | Meaning | Example (age must be 13 to 19) |
|---|---|---|
| **Normal** | valid, typical data; should be accepted | 16 |
| **Boundary** | data **at the edge** of the valid range, both just inside and just outside | 13, 19 (accepted); 12, 20 (rejected) |
| **Erroneous** | the wrong type or clearly invalid; should be rejected | "abc", −5, empty input |

Example test plan for "age 13 to 19":

| Test data | Type | Expected result |
|---|---|---|
| 16 | normal | accepted |
| 13 | boundary | accepted |
| 19 | boundary | accepted |
| 12 | boundary | rejected, error message |
| 20 | boundary | rejected, error message |
| "abc" | erroneous | rejected, error message |

The expected outcome must be written **before** running the test. Fixing a bug means **re-running all the tests**, because a change can break something else.

### Finding and fixing errors

1. Read the error message (type and line number).
2. Check the line and the lines just before it.
3. Use **print statements** or a **trace table** to see the variable values.
4. Test with small, simple data where you know the answer.
5. Fix one thing at a time, then re-test.

### Evaluating a program

To judge a program, ask: does it meet the **requirements**? Does it work for **all** valid inputs and handle invalid ones (**robust**)? Is the code **readable** (names, comments, indentation) and **efficient**? **Strengths** might be: validated input, clear structure with subprograms. **Weaknesses**: no validation, repeated code, global variables, unclear names. **Improvements** should be specific: "add a range check on the mark", "move the repeated code into a function".

## Key terms and definitions

- **Subprogram**: a named block of code that carries out a specific task and can be called from elsewhere in the program.
- **Procedure**: a subprogram that carries out a task but does not return a value.
- **Function**: a subprogram that returns a value to the code that called it.
- **Parameter**: a variable named in a subprogram definition that receives a value passed in when the subprogram is called.
- **Local variable**: a variable that can only be used inside the subprogram where it is declared.
- **Global variable**: a variable that can be used anywhere in the program.
- **Validation**: an automated check that data entered is reasonable and acceptable for the program to process.
- **Syntax error**: an error where the code breaks the rules of the programming language.
- **Runtime error**: an error that causes the program to crash while it is running.
- **Logic error**: an error where the program runs but does not produce the correct result.
- **Test plan**: a table listing test data, its type, and the expected outcome for each test.
- **Boundary data**: test data on or next to the limits of what is accepted.
- **Erroneous data**: test data that should be rejected because it is invalid.

## Worked examples

**1. A program accepts a mark from 0 to 100 inclusive. Complete a test plan with one item of normal, boundary and erroneous data. [3]**

Normal: 55 → accepted (1). Boundary: 100 (accepted) or 101 (rejected) or 0 / −1 (1). Erroneous: "ten" (a string) → rejected with an error message (1). Each needs the **expected outcome** to earn the mark.

**2. Write a function in Python (or pseudocode) that takes the length and width of a rectangle and returns its area, and show how it is called. [4]**

result = area(5, 3)

```

Marks: function definition with two parameters (1), correct calculation (1), `return` (1), call with arguments and the result used (1).

(a) A **logic** error (1): the program runs but gives wrong output. (b) `avg = (a + b) / 2` (1), because division is done before addition.

Length check: at least 8 characters (1). Presence check: the field is not empty (1). (Also accept a format check, e.g. must contain a digit.)

## Common mistakes

- Saying validation proves the data is **correct**. It only checks it is **sensible**; "verification" or double entry is about accuracy.
- Writing boundary data that is not on the edge. For 0–100, use 0, 100, and (just outside) −1, 101; 50 is normal.
- Forgetting the **expected outcome** column in a test plan.
- Mixing up error types: a crash while running is **runtime**; wrong answer with no crash is **logic**; a typo in the code is **syntax**.
- Defining a function but never calling it, or calling it and not storing the returned value.
- Confusing parameter (in the definition) with argument (the actual value passed).
- Changing a global variable inside a function without `global` (Python creates a new local one).
- A validation loop that does not ask again inside the loop, so it repeats forever or just stops.
- Saying testing "proves there are no errors": it only shows errors are present or that tests pass.
