# Algorithm design: development cycle, flowcharts and pseudocode

> **In the exam:** This is **Paper 2 (Algorithms, Programming and Logic, 1 h 45, 75 marks)** territory, and the **program development life cycle** and structure diagrams can also appear in Paper 1-style short answers. Typical items: 1–2 mark definitions (decomposition, abstraction), completing or drawing a **flowchart**, reading pseudocode and **stating its purpose**, completing a **trace table**, and writing or correcting short algorithms in **Cambridge pseudocode**. Flowchart/pseudocode questions are often 4–8 marks.

## What you need to know

- The stages of the **program development life cycle**: **analysis, design, coding, testing**.
- **Computational thinking**: **abstraction**, **decomposition** and **pattern recognition**.
- Analysis: identifying the **inputs, processes, outputs and storage** and the **requirements**.
- Design tools: **structure diagrams**, **flowcharts**, **pseudocode**.
- **Flowchart symbols** and how to use them.
- **Cambridge pseudocode**: declaring variables, constants, assignment, input/output, selection, iteration, operators.
- Explain the **purpose of an algorithm** from pseudocode or a flowchart, and **trace** it.

## Notes

### The program development life cycle

| Stage | What happens |
|---|---|
| **Analysis** | Decide **exactly what the program must do**. Use **abstraction** (ignore unnecessary detail) and **decomposition** (break the problem into smaller parts). Identify **inputs, processes, outputs, storage** and the **requirements** (what the user needs) |
| **Design** | Plan the solution using **structure diagrams, flowcharts and pseudocode** |
| **Coding** | Write the program in a programming language and **test it as it is written** (iterative testing) |
| **Testing** | Run the program with **test data** to find errors, then fix them. Repeat until it works |

### Computational thinking

- **Abstraction:** keeping only the **important details** and hiding/removing the ones that are not needed. E.g. a map of the Underground shows stations and lines but not exact distances.
- **Decomposition:** **breaking a complex problem into smaller sub-problems** that are easier to solve, each solved by its own subroutine. Different people can work on them at the same time.
- **Pattern recognition:** finding **similarities** between parts of a problem so one solution can be reused.

### Structure diagrams

A **structure diagram** shows decomposition as a **hierarchy**: the main problem at the top, broken into sub-tasks in boxes below, and again into smaller sub-tasks. It shows *what* has to be done, not the order. Example for an *online quiz*:

```
                    Online quiz
        ┌──────────────┼───────────────┐
   Log in user     Ask questions    Show result
                   ┌─────┴─────┐
              Read question  Check answer
```

### Inputs, processes, outputs and storage

For a program that calculates a customer's bill:

- **Inputs:** items bought, quantities. **Processes:** multiply price × quantity, add them, apply discount. **Outputs:** total shown on the receipt. **Storage:** price list file, sales record.

### Flowchart symbols

| Symbol | Shape | Use |
|---|---|---|
| **Terminator** | Rounded rectangle (oval) | **START** and **END** |
| **Process** | Rectangle | An instruction or calculation, e.g. `Total ← Total + Price` |
| **Decision** | Diamond | A **yes/no question** with two exits (**Yes/No** or **True/False**) |
| **Input/Output** | Parallelogram | `INPUT` and `OUTPUT` |
| **Subroutine/predefined process** | Rectangle with **double vertical side lines** | Call a procedure/function |
| **Flow line** | Arrow | Shows the direction of flow |

Rules: one START at the top; arrows show direction; every decision has **two labelled exits**; a **loop** is made by an arrow going **back up** to before a decision.

### Cambridge pseudocode: the essentials

The syllabus gives a pseudocode guide. Use these forms exactly. Keywords are **UPPER CASE**; indent code inside structures; comments start with `//`.

**Data types:** `INTEGER`, `REAL`, `CHAR`, `STRING`, `BOOLEAN`.

```
DECLARE Age : INTEGER
DECLARE Name : STRING
CONSTANT Pi ← 3.142
```

**Assignment** uses `←`:

```
Total ← 0
Total ← Total + Price
```

**Input and output:**

```
INPUT Name
OUTPUT "Hello ", Name
```

**Operators:** `+ - * /`, `^` (power), `MOD` (remainder), `DIV` (whole-number division), `&` joins strings; comparisons `= <> < > <= >=`; logic `AND OR NOT`.

`17 DIV 5 = 3` and `17 MOD 5 = 2`.

**Selection:**

```
IF Mark >= 50 THEN
   OUTPUT "Pass"
ELSE
   OUTPUT "Fail"
ENDIF
```

```
CASE OF Grade
   "A" : OUTPUT "Excellent"
   "B" : OUTPUT "Good"
   OTHERWISE OUTPUT "Check your result"
ENDCASE
```

**Iteration (three loop types):**

```
FOR Count ← 1 TO 10
   OUTPUT Count
NEXT Count
```
```
WHILE Password <> "secret" DO
   INPUT Password
ENDWHILE
```
```
REPEAT
   INPUT Number
UNTIL Number > 0
```

| Loop | Use when | Condition checked |
|---|---|---|
| **FOR** (count-controlled) | You know **how many times** | Built in |
| **WHILE** (pre-condition) | Might run **zero** times | **Before** each loop |
| **REPEAT…UNTIL** (post-condition) | Must run **at least once** | **After** each loop; stops when the condition is **true** |

### Example algorithm: totalling and averaging

```
Total ← 0
FOR Count ← 1 TO 5
   INPUT Score
   Total ← Total + Score
NEXT Count
Average ← Total / 5
OUTPUT "Average = ", Average
```

Always **initialise** (`Total ← 0`) before the loop.

### Explaining the purpose of an algorithm

Say **what it achieves overall**, not each line. E.g. "It inputs 5 scores, adds them up and outputs the average." Marks are not given for "it has a loop".

## Key terms and definitions

- **Algorithm:** an ordered set of steps to solve a problem.
- **Decomposition:** breaking a complex problem into smaller, more manageable parts.
- **Abstraction:** removing unnecessary detail so only the important features of a problem remain.
- **Pseudocode:** a way of writing an algorithm using structured English-like statements, not tied to a particular programming language.
- **Flowchart:** a diagram that uses symbols and arrows to show the steps of an algorithm.
- **Structure diagram:** a hierarchical diagram showing a problem broken down into sub-problems.
- **Constant:** a named value that cannot change while the program runs.
- **Variable:** a named memory location whose value can change.
- **Iteration:** repeating a set of instructions.
- **Selection:** choosing which instructions to run depending on a condition.

## Worked examples

**1.** *Describe what is meant by decomposition and give one benefit. [2]*

- Breaking a problem into **smaller sub-problems/parts** [1]
- Benefit: **easier to solve/test**, or **can be shared among a team** [1]

**2.** *Write pseudocode that inputs a number and outputs "Positive" if it is more than 0, "Negative" if it is less than 0 and "Zero" otherwise. [4]*

```
INPUT Number
IF Number > 0 THEN
   OUTPUT "Positive"
ELSE
   IF Number < 0 THEN
      OUTPUT "Negative"
   ELSE
      OUTPUT "Zero"
   ENDIF
ENDIF
```

Marks: input [1], first IF and output [1], second condition [1], final output and all `ENDIF`s [1]. (`ELSEIF` is not in the Cambridge guide; nest the IFs.)

**3.** *State the purpose of this algorithm. [2]*

```
INPUT Number
Count ← 0
WHILE Number <> -1 DO
   Count ← Count + 1
   INPUT Number
ENDWHILE
OUTPUT Count
```

- It counts how many numbers are input [1] before the sentinel/stop value −1 is entered [1].

## Common mistakes

- Using `=` for assignment. In Cambridge pseudocode **assignment is `←`**; `=` is a comparison.
- Forgetting to **initialise** totals and counters, or forgetting `ENDIF`, `ENDWHILE`, `NEXT`.
- Flowchart **decision with only one exit**, or exits not labelled Yes/No.
- Using a **rectangle for input/output** or a diamond for a process.
- Confusing **decomposition** (splitting the problem) with **abstraction** (removing detail).
- Describing the **lines** of an algorithm instead of its **purpose**.
- Using `REPEAT…UNTIL` with the condition the wrong way round: it **stops when the condition is true**.

## Practice questions

1. Name the four stages of the program development life cycle in order. [2]
2. State the flowchart symbol used for (a) a decision and (b) input/output. [2]
3. Explain the difference between abstraction and decomposition. [2]
4. Evaluate: (a) `23 MOD 5` (b) `23 DIV 5` (c) `2 ^ 3` [3]
5. Write pseudocode that asks the user to enter a number between 1 and 10 repeatedly until they enter a valid value. [4]
6. Write pseudocode using a FOR loop that outputs the 5 times table from 5 × 1 to 5 × 12. [3]
7. State the purpose of this algorithm: `Total ← 0; FOR N ← 1 TO 10: INPUT X; IF X > Total THEN Total ← X ENDIF; NEXT N; OUTPUT Total`. Assume all inputs are positive. [2]
8. State two differences between a WHILE loop and a REPEAT…UNTIL loop. [2]

<details><summary>Answers</summary>

1. Analysis, design, coding, testing [2 marks if all four in this order; 1 mark if three are correct].
2. (a) Diamond; (b) parallelogram.
3. Abstraction removes unnecessary detail/keeps only what matters [1]; decomposition splits a problem into smaller parts [1].
4. (a) 3 [1] (b) 4 [1] (c) 8 [1].
5. ```
REPEAT
   INPUT Number
UNTIL Number >= 1 AND Number <= 10
```
   REPEAT [1], INPUT [1], condition correct [1], UNTIL/closing [1]. (A WHILE solution with a first INPUT before the loop is also acceptable.)
6. ```
FOR N ← 1 TO 12
   OUTPUT 5 * N
NEXT N
```
   Correct FOR limits [1], output of 5 × N [1], NEXT [1].
7. It finds [1] the largest number [1] of the ten input numbers (works because all inputs are positive).
8. WHILE checks the condition **before** the loop, so it may run zero times; REPEAT checks **after**, so it runs at least once [1]. WHILE runs while the condition is true; REPEAT stops when it becomes true [1].
